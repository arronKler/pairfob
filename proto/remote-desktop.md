# Remote desktop

The macOS 13+ host advertises optional GetConfig booleans `setup_desktop`, `view_desktop`, `control_desktop` and `listen_desktop_audio`. A missing key means false. `setup_desktop` is true when the host OS supports local desktop setup (macOS 13+) and direct P2P transport is enabled, even before desktop access is granted (`view_desktop: false`), and false on unsupported hosts (such as Linux) or when P2P direct transport is disabled. Clients can use `(view_desktop, setup_desktop)` to distinguish unsupported hosts (`false, false`), unconfigured macOS 13+ hosts (`false, true`), and enabled hosts (`true, *`). On the Mac, run `pairfob desktop enable` for viewing or `pairfob desktop enable-control` for viewing and input. Use `pairfob desktop status` to inspect the setting and `pairfob desktop disable` to revoke it. The paired PWA's Computers page offers Remote desktop on an enabled host. Reconnect the paired PWA after changing the host setting to refresh capabilities. A live direct application session is required.

Interactive macOS installation offers one-time unattended access. Run `pairfob desktop setup` later after a non-interactive install, or `enable` / `enable-control` to change a saved decision. On the Mac, choose the main display (follows the current main display) or a particular display, and allow Screen Recording plus Accessibility for control. All devices paired to this daemon, including devices paired later, can reconnect within that grant. Remote opens only check system permissions. If macOS still needs a grant, complete it locally in System Settings and use `desktop status` to check readiness. Older per-open approvals require one new unattended decision. The Mac menu stops the current stream. Disabling desktop access or unpairing the device revokes future access. The computer must remain awake and unlocked.

All four requests run inside the existing v1 encrypted RPC envelope on one established P2P epoch. DesktopOpen takes a fresh operation_id, recvonly SDP offer, control and audio booleans, and quality (balanced, detail or motion). The Mac reserves one pending or active slot. Once capture starts it returns sdp (answer), display (local name), control and audio. The open operation ID becomes the desktop_id. Desk media uses a separate DTLS-SRTP peer with host and STUN-derived ICE candidates, UDP or direct TCP. Neither endpoint configures TURN. The origin does not forward screen, sound, input or desktop SDP.

DesktopPing takes desktop_id. Once activated the browser renews every second. The host allows twelve seconds for the first renewal and four seconds thereafter. DesktopClose takes desktop_id and a fresh operation_id and can cancel a pending start. Its successful reply means the capture process has exited and the host can accept the next desktop session. Closing, logout, screen lock, route teardown and lease loss terminate capture and release pressed mouse buttons. Local policy is rechecked during the session. Local audit records contain the device ID and the approved access mode. Input contents and display data are excluded.

DesktopInput takes desktop_id, sequence (starts at one, strictly consecutive), operation_id (desktop_id plus underscore and decimal sequence), and event. Mouse coordinates are normalized within the selected display. Events are move, down, up, scroll, text, key and release. Key modifiers use Shift=1, Control=2, Option=4, Command=8. A key is a complete press and release. Successful input acknowledges admission into the local input queue. Outcomes are never replayed across a disconnect. The UI coalesces queued moves and retains ordered button edges. See rpc.schema.json for wire fields.

Capture uses ScreenCaptureKit and hardware H.264. Presets bound the long edge to 1920/60, 2560/30 or 1280/60 respectively. The sender honors rate-limited PLI/FIR keyframe requests, reduces bitrate on receiver loss or REMB and recovers toward the selected preset ceiling as delivery improves. Optional system audio uses stereo Opus at 48 kHz with 20 ms audio packets. A fresh session is required to change the display, quality or permissions. To change the authorized display or access scope, rerun the local enable command.

A desktop host can return optional frame observations on the existing direct DesktopPing. A new viewer first sends the original ping. If the reply includes an unsigned 32-bit `rtp_time` and the browser reports RTP timestamps on presented video frames, subsequent pings include `observe: true`. Such a host can stop repeating idle video. The timestamp identifies the last completely written video frame, including the RTP packetizer offset. A `healthy` observation requires fresh capture evidence and delivery of the corresponding screen revision. Both conditions and an exact match with the browser's last presented RTP timestamp let a static desktop stay interactive. A viewer or host without this exchange keeps periodic video refresh.

When the picture stops advancing without matching proof, the viewer pauses input after 1.8 seconds, discards queued input, releases held buttons and can request a keyframe with `keyframe: true` on the same ping, at most once every two seconds. Six and a half seconds without presentation or matching proof ends an established stream. A first frame has a separate 15-second timeout. A recent `encode_ms` sample measures native hardware encoder submission to its output callback. The connection details panel uses receiver counters for mean jitter-buffer and decode times, and browser frame metadata for compositor submission to expected display. These clocks and the ICE round-trip measurement are independent.
